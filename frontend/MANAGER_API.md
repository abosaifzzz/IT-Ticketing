# Manager API integration

API mode connects manager dashboard, all-ticket search/filtering/details, assignment/reassignment, manual support tickets, department and fault-category/subcategory administration, IT-user administration and reports. Explicit development mock mode keeps the original pages; real sessions never mount mock feature data. Shared inventory, notifications and the live bell are now connected; see ASSETS_NOTIFICATIONS_API.md.

Dashboard totals/status counts, recurring problems and engineer workload come from server queries. Dashboard and ticket pages refresh on focus and every 15 seconds, with manual refresh controls. All Tickets keeps one status filter and adds no duplicate assignment selector. Department/category filters include inactive references for historical ticket searches; creation options use active references only.

Assignment uses POST /tickets/:id/assignment with the current expectedVersion. Active unavailable engineers remain selectable and display temporary unavailability plus activeTicketCount. Inactive accounts and manager identities are excluded. Conflicts reload the ticket and engineer list without silently replaying the assignment. Manager/self-claim identity and all historical events remain server snapshots. Details display both public/internal notes and employee comments.

Manual-ticket assignment is optional and defaults to no engineer. The POST /tickets payload includes assignedTechnicianId only when explicitly selected, allowing the server to create and assign transactionally. Reporter name and department are manually required for employees and senior management; senior management also requires position. Creator and owner identities are never submitted. In-memory idempotency keys support retry after a lost response.

Reference writes use POST/PATCH /departments, /fault-categories and /fault-subcategories. Ticket counts and historical snapshots come from the server. IT users use /it-users with exactly technician and manager roles. Forms/API adapters include no phone, extension or password fields. New identities require separate private credential provisioning through existing backend tools; the management UI does not fabricate credentials. Account deactivation/role changes use server session-revocation rules.

Reports read GET /reports with dateFrom/dateTo and limit. All four counts and both rankings come directly from the server. CSV uses GET /reports/export.csv with the same filters through the cookie-authenticated HTTP client; the browser downloads the returned file without recalculating or serializing report data. Invalid date ranges disable export. No performance, priority, rating or manual-maintenance reports were added.

Checks: npm run lint; npm run build; npm run verify:api-manager; npm run verify:manager-browser. The live browser suite uses the existing backend/.env.fresh.test database and fictional accounts/records, cleans its own fixtures, and needs no administrator login. It checks role restrictions, assignment to unavailable engineers, version conflicts, persistence, reference/user create/edit/activation, optional manual assignment, historical labels, server report/date/CSV behavior, Arabic RTL at mobile/tablet/desktop widths, both themes and assignments appearing in engineer queue/details. Existing auth/employee/engineer suites remain regression checks.

If C: has no temporary space, set TEMP and TMP to a writable directory on D: before running node scripts/verify-manager-browser.mjs directly. Test artifacts remain ignored under artifacts.local. Production same-origin HTTPS and private real-account provisioning remain deployment tasks.
