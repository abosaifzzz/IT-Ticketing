# Backend — Node.js + MySQL

Independent system administration (`admin`, without manager inheritance) is documented in [Administration API and private setup](docs/administration.md). Migration 016 adds safe administration tables, restricted audit grants, protected account recovery, monitoring and encrypted backup jobs. No default administrator is created; HTTP restoration remains disabled.

The preferred simple asset/type/group/custody API is now `/api/asset-management/simple`. See [the simple API contract](docs/simple-assets.md). Existing endpoints remain for compatibility; complex ledger, QR, approval and advanced-report workflows are not required by the simple module.

Comprehensive asset management now extends the existing inventory under `/api/asset-management`. See [the complete frontend API contract, schema mapping, setup and limitations](docs/asset-management.md). Apply migration 012 using the private local migration workflow; existing legacy assets remain unchanged until explicit manager conversion.

Local account passwords now accept any non-empty value without a minimum-length or composition rule, as requested for manual testing. The existing 1,024 UTF-8 byte processing cap remains. Use `npm run user:password -- "account-email"` to set passwords privately; only Argon2id hashes are stored and a reset revokes previous sessions. This policy does not change database-administrator or database-application credentials.

Employee ticket selection backend is available through `/api/employee-options` and `reporterEmployeeId` on ticket creation. See [frontend integration contract](docs/employee-ticket-selection.md). Frontend implementation is pending; existing manual forms still work.

Ticket references now use `IT0`, `IT1`, `IT2`, ? after migration 009. UUIDs remain internal. See [ticket reference setup and verification](docs/ticket-references.md).

## دليل الموظفين اليدوي

دليل الموظفين متاح للمدير والمهندس فقط في `/it/employees`. بعد الترحيلين 007 و008، يقبل `POST /api/employees` الاسم الكامل والقسم النشط فقط: `{ "fullName": "اسم تجريبي", "departmentId": "UUID" }`. أُلغي كود الموظف بطلب المالك. يعيد `GET /api/employees?search=&page=1` الشكل `{ items, total, page, pageSize }` مع 25 سجلًا في الصفحة وبحث بالاسم. استُورد 132 موظفًا و20 قسمًا من الملف المعتمد إلى قاعدة التطوير؛ لم تُنشأ حسابات دخول أو كلمات مرور ولم تتغير ملكية البلاغات أو نماذج إنشائها. التفاصيل والأوامر ونتائج الاختبارات في [توثيق دليل الموظفين والاستيراد](docs/employees.md).

المراجعة المحلية الأحدث: [دليل الإعداد والتحقق الكامل والقيود الإنتاجية](../LOCAL_VERIFICATION.md). الواجهة متصلة الآن بجميع واجهات API المطلوبة. أكد المالك تنفيذ دفعة الترحيلات الخاصة بالأصول والإشعارات محليًا؛ تحقق الفحص اللاحق من الجداول وصلاحيات القراءة في قواعد التطوير والاختبار. وضع API هو الوضع العادي، ولا تعني الاختبارات المحلية الجاهزية للنشر.

المراجعة الشاملة الأحدث: [تطابق خدمات الواجهة، توثيق API، الأمان، والتحقق والعوائق المتبقية](docs/api-parity.md). أُضيفت ملخصات تكرار الأعطال ولوحات الأدوار وإحصاءات المخزون وبحث الإدارة وأعداد البلاغات وتهيئة كلمات المرور المحلية بصورة خاصة وإلغاء الجلسات. تحقق `npm run check:fresh` من جميع الوحدات على قاعدة تدقيق جديدة مستقلة، مع الترحيلات من الصفر وإعادة تشغيلها؛ لا يغير قواعد التطوير والاختبار السابقة.

توثيق الوحدات الجديدة: [تقارير المدير](docs/reports.md) و[الإشعارات والبث والتحديث الدوري](docs/notifications.md). التقارير مكتملة على الجداول الحالية دون ترحيل إضافي. يتطلب تشغيل الإشعارات ترحيل `006` وصلاحياته؛ وقد طُبّق مع `005` محليًا في قواعد التطوير والاختبار خلال المراجعة الأخيرة. حالة التنفيذ والتشغيل الأحدث موضحة في هذين المستندين.

يتضمن الخادم المصادقة المحلية وإدارة البيانات المرجعية ومستخدمي تكنولوجيا المعلومات ودورة التذاكر، وواجهات مخزون الأصول والتصدير والسحب. يتطلب تشغيل واجهات الأصول تطبيق `005_assets.sql`؛ يمكن تجميع الترحيلات وتطبيقها لاحقًا في دفعة واحدة حسب طلب مالك المشروع. أُضيفت واجهات التقارير والإشعارات؛ راجع توثيق الوحدات أعلاه لحالة الترحيل. الواجهة متصلة الآن بالمصادقة ووحدات الأعمال الفعلية، مع وضع تجريبي صريح للتطوير فقط.

## الإعداد المحلي

### إعداد MySQL محليًا على Windows

بعد تثبيت MySQL Server وتشغيله على المنفذ `3307`، يمكن تنفيذ الإعداد المحلي مرة واحدة من `backend/`:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\setup-local-db.ps1
```

يطلب الأمر كلمة مرور `root` الحالية وكلمة مرور جديدة للتطبيق لا تقل عن 16 حرفًا داخل PowerShell مع إخفاء الإدخال. لا تكتب كلمات المرور في المحادثة أو سطر الأوامر. تُحذف متغيرات الإعداد المؤقتة عند انتهاء العملية، ولا تُحفظ كلمة مرور الإدارة. يفحص الأمر الخادم وقواعد البيانات قبل إنشاء الموارد، ويشترط MySQL 8.0 أو 8.4 مع InnoDB و`dynamic` وصفحات بحجم 16KB، ويرفض MariaDB. يتوقف عند اختلافها لمراجعة توافق الترحيل قبل إجراء تغييرات.

ينشئ قاعدتين جديدتين فقط: `hospital_it_helpdesk_dev` و`hospital_it_helpdesk_test` بترميز `utf8mb4`، وحسابين محليين منفصلين: `helpdesk_dev` و`helpdesk_test`. يرفض إعادة استخدام قاعدة أو حساب موجود، أو الكتابة فوق ملفات البيئة المحلية. يشغّل ترحيل المصادقة الحالي مرتين لكل قاعدة بحساب الإدارة، ويتحقق من الجداول والاتصال وعمليات المستودعات باستخدام معاملة يجري التراجع عنها.

تحصل حسابات التطبيق على `SELECT` و`INSERT` و`UPDATE` و`DELETE` لجدولي `users` و`auth_sessions` في القاعدة الخاصة بكل حساب. تحصل على `SELECT` و`INSERT` و`UPDATE` لجداول البيانات المرجعية الثلاثة؛ ويضاف `DELETE` لهذه الجداول في قاعدة الاختبار فقط لتنظيف سجلات الاختبارات. لا تمتلك صلاحيات إنشاء الجداول أو إدارة المستخدمين أو الوصول إلى سجل الترحيلات. لذلك تحتاج الترحيلات إلى بيانات اتصال إدارة تُقدّم بصورة خاصة للعملية؛ لا تشغّلها بحساب التطبيق.

لتحديث قواعد التطوير والاختبار الموجودة دون إعادة إنشاء قواعد أو حسابات أو تغيير ملفات البيئة:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\migrate-local-db.ps1
```

يطلب الأمر كلمة مرور الإدارة بشكل مخفي، ويطبق الترحيلات مرتين لكل قاعدة للتحقق من إعادة التشغيل، ثم يتحقق من البصمات ويضيف صلاحيات الجداول الجديدة للحسابات الحالية فقط. يضيف `002_reference_data.sql` جداول `departments` و`fault_categories` و`fault_subcategories` وحالة `is_available` للمستخدمين. لا يغير ترحيل المصادقة السابق ولا كلمات المرور أو سجلات المستخدمين الحالية.

يُحفظ اتصال التطوير في `.env` واتصال الاختبار في `.env.test`؛ يتجاهل Git الملفين. لا يختار `NODE_ENV=test` ملف الاختبار تلقائيًا. لاستخدامه في جلسة PowerShell:

```powershell
$env:DOTENV_CONFIG_PATH = '.env.test'
npm start
Remove-Item Env:DOTENV_CONFIG_PATH
```

لا يحذف الإعداد قواعد البيانات الموجودة ولا يعدّل الواجهة الأمامية. إذا توقف بعد إنشاء بعض الموارد، افحص الحالة قبل أي محاولة أخرى؛ لا يحذف الموارد الجزئية تلقائيًا.

يتطلب Node.js 20.18 أو أحدث، وخادم MySQL يمكن الوصول إليه. أنشئ قاعدة بيانات UTF-8، مثلًا:

```sql
CREATE DATABASE hospital_it_helpdesk CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
```

انسخ `.env.example` إلى `.env`، ثم أدخل بيانات اتصال MySQL المحلية الخاصة بك. لا تضع كلمة مرور قاعدة البيانات في Git، ولا تستخدم حساب MySQL ذي صلاحيات عامة في التشغيل الفعلي. اضبط `APP_ORIGIN` على عنوان الواجهة بدقة؛ القيمة الافتراضية هي `http://localhost:5173`.

```bash
cd backend
npm install
npm run db:migrate
npm run user:create -- "employee@example.com" "اسم الموظف" employee
npm run dev
```

أمر إنشاء المستخدم يطلب كلمة المرور داخل الطرفية ولا يقبلها كوسيط في سطر الأوامر. الأدوار المسموحة: `employee` و`technician` و`manager`. لا توجد صفحة تسجيل حسابات عامة، ولا توجد كلمات مرور افتراضية. استعمل حسابات وأسماء تجريبية فقط أثناء التطوير.

## مسارات المصادقة

- `POST /api/auth/login` — JSON يحتوي `email` و`password`؛ يعيد بيانات مستخدم محدودة ويضبط ملف ارتباط جلسة `HttpOnly`.
- `GET /api/auth/me` — يعيد هوية صاحب الجلسة الحالية.
- `POST /api/auth/logout` — يبطل الجلسة على الخادم.
- `GET /api/health` — فحص تشغيل العملية؛ لا يفحص جاهزية قاعدة البيانات.

طلبات `POST` تتطلب ترويسة `Origin` المطابقة لـ`APP_ORIGIN`. في التطوير، اسم ملف الارتباط `it-helpdesk-session`؛ وفي الإنتاج يُستخدم `__Host-it-helpdesk-session` مع `Secure` و`HttpOnly` و`SameSite=Strict`. لا يُعاد رمز الجلسة في JSON ولا يُحفظ في `localStorage`؛ تُخزن في قاعدة البيانات بصمته فقط. يلزم HTTPS في الإنتاج.

```bash
npm run lint
npm test
npm run test:integration
```

`npm test` (أو `npm run test:unit`) يشغّل الاختبارات المعزولة دون الحاجة إلى قاعدة بيانات. يشغّل `npm run test:integration` خادم HTTP مؤقتًا ومستودعات MySQL الحقيقية، ويقرأ إعدادات الاتصال مباشرة من `.env` و`.env.test` دون عرض كلمات المرور. يجب تشغيل MySQL وتطبيق ترحيل المصادقة مسبقًا؛ يفشل الاختبار عند تعذر الاتصال ولا يُعلن نجاحًا وهميًا بتجاوز الاختبارات.

يتحقق الاختبار الحي من اتصال التطوير للقراءة فقط، ويرفض الكتابة خارج `hospital_it_helpdesk_test` أو استخدام حساب `root`. ينشئ حسابات خيالية بأسماء بريد فريدة تحت `@demo.example` وكلمة مرور عشوائية داخل الذاكرة. يتحقق من إنشاء الحسابات والتحقق من المدخلات ومنع تكرار البريد، ومن تجزئات Argon2id المملحة وغياب كلمة المرور الصريحة عن السجل المحفوظ، ومن هوية الأدوار الثلاثة، وملف الارتباط `HttpOnly`، وحفظ بصمة رمز الجلسة فقط، والاستعادة عبر نسخة خادم جديدة، والخروج والانتهاء وتعطيل الحساب. يحذف فقط معرفات الحسابات التي أنشأها التشغيل نفسه وجلساتها، دون تفريغ الجداول أو تعديل حسابات التطوير.

إنشاء الحسابات المحلية موجود في `src/auth/localAccountService.js` ويستخدمه أمر `user:create` والاختبار الحي معًا. تظل المصادقة خلف واجهة `provider.authenticate({ email, password })` المحقونة في `createAuthService`؛ يعيد المزود هوية حساب موثوقة أو `null`، بينما تدير خدمة المصادقة الجلسات والبيانات العامة. لا تتصل المسارات بمزود كلمات المرور مباشرة. يمكن استبدال المزود مستقبلًا مع ربط الهوية الخارجية بحساب محلي؛ لم تُنفذ أي خدمة هوية خارجية الآن.

## واجهات البيانات المرجعية ومستخدمي تكنولوجيا المعلومات

تحتاج المسارات أدناه إلى جلسة مصادقة؛ وتُقرأ هوية المستخدم ودوره وحالة حسابه من قاعدة البيانات عند كل طلب. يلزم `Origin` مطابق لـ`APP_ORIGIN` عند التعديل، بما في ذلك `PATCH`. تعيد القوائم `{ items: [...] }` والسجلات `{ item: ... }`، ولا تعيد بيانات اعتماد أو رموز جلسات. الأخطاء: `400` للمدخلات غير الصالحة، و`401` للجلسة الغائبة أو المنتهية، و`403` للصلاحيات، و`404` للسجل غير المرئي أو غير الموجود، و`409` للتكرار أو تعارض حالة النوع الرئيسي.

| المسار | GET | POST وPATCH /:id للمدير فقط |
| --- | --- | --- |
| `/api/departments` | الأقسام | `name`, `isActive` |
| `/api/fault-categories` | أنواع الأعطال الرئيسية | `name`, `isActive` |
| `/api/fault-subcategories` | الأنواع الفرعية؛ تصفية اختيارية بـ`?categoryId=UUID` | `name`, `categoryId`, `isActive` |
| `/api/it-users` | حسابات تكنولوجيا المعلومات | `email`, `fullName`, `role`, `isActive` |

يدعم كل مسار أيضًا `GET /:id`. يرى المدير جميع السجلات، بينما يرى الموظف والمهندس الأقسام والأنواع النشطة فقط. لا يظهر النوع الفرعي ضمن الخيارات إلا إذا كان هو ونوعه الرئيسي نشطين. لا تعطل حالة الأب سجلات الأبناء نفسها؛ يؤدي تفعيل الأب إلى إظهار أبنائه النشطين مجددًا. يجب أن يكون الأب موجودًا، ولا يمكن إنشاء نوع فرعي نشط أو تفعيله تحت أب غير نشط. الأسماء فريدة للأقسام والأنواع الرئيسية، وفريدة داخل النوع الرئيسي للأنواع الفرعية. يتحقق الخادم من UUID، وأطوال النصوص، ونوع القيم المنطقية، ويرفض الحقول غير المعروفة.

في حسابات تكنولوجيا المعلومات، الدوران الوحيدان هما `technician` و`manager`. لا تعرض الإدارة حسابات `employee` ولا تسمح بتحويلها من هذه المسارات. تعيد الخيارات لغير المديرين المهندسين النشطين فقط بالحقول `id`, `fullName`, `isAvailable`، دون البريد أو بيانات المديرين أو الحسابات غير النشطة. يشمل ذلك المهندسين غير المتاحين مؤقتًا لتمييز عدم التوفر عن تعطيل الحساب. تعيد إدارة المدير `isAvailable: null` لحسابات المديرين.

يمكن للمهندس النشط تعديل توفره فقط عبر `PATCH /api/it-users/me/availability` بجسم `{ "isAvailable": false }` أو `true`. يؤخذ المعرف من الجلسة؛ لا يمكن تعديل توفر شخص آخر، ولا يُقبل حقل التوفر ضمن تعديل المدير العام. لا توجد مسارات حذف؛ يستخدم المدير `PATCH` مع `isActive: false` للتعطيل. تحفظ التعديلات المعرفات الثابتة، ولا توجد عمليات تعيد كتابة أسماء تاريخية أو تعدل بيانات التذاكر. عند تنفيذ التذاكر لاحقًا، يجب حفظ أسماء مرجعية كلقطات تاريخية مستقلة عن الاسم الحالي.

تُرفض حقول الهاتف والتحويلة وكلمات المرور وتجزئاتها ومزود الهوية في مسارات الإدارة. تنشئ إدارة مستخدمي تكنولوجيا المعلومات سجل هوية دون كلمة مرور (`password_hash` فارغ)، وبالتالي لا يمكن لهذا السجل تسجيل الدخول بكلمة مرور قبل تزويده ببيانات اعتماد عبر مسار إداري منفصل مستقبلًا. لا تولد الإدارة كلمات مرور افتراضية، ولا تُنفذ الآن مزود هوية خارجيًا. يبقى أمر `user:create` المنفصل متاحًا لإنشاء حساب محلي جديد بكلمة مرور خاصة في الطرفية.

تشمل الاختبارات الحية المصادقة وإدارة البيانات المرجعية والتذاكر ودورة العمل والتزامن. تستخدم حسابات وبيانات خيالية فريدة داخل قاعدة الاختبار وتحذف سجلات تشغيلها فقط، ولا تعدل الواجهة الأمامية.

## إنشاء تذاكر الدعم والاستعلام عنها

يضيف `003_tickets.sql` جدولي `tickets` و`ticket_history`، ويضيف `004_ticket_workflow.sql` حقول دورة العمل وإصدار التذكرة وتفاصيل أحداث السجل دون تغيير ملفات الترحيلات السابقة. شغّل أمر `migrate-local-db.ps1` المذكور أعلاه على القواعد الموجودة؛ يمنح حساب التطوير `SELECT, INSERT, UPDATE` على التذاكر و`SELECT, INSERT` على السجل، ويمنح حساب الاختبار صلاحيات التنظيف اللازمة. لا توجد واجهة حذف تذاكر أو تعديل حر للسجلات أو الأحداث السابقة.

| الطريقة والمسار | الوظيفة |
| --- | --- |
| `POST /api/tickets` | إنشاء تذكرة شخصية أو بالنيابة أو بلاغ دعم يدوي |
| `GET /api/tickets` | قائمة محكومة بهوية الجلسة مع البحث والتصفية والترقيم |
| `GET /api/tickets/:id` | التفاصيل وسجل الإنشاء والإسناد الأولي إن وُجد |

تتطلب جميع المسارات جلسة نشطة. يحصل الموظف على تذاكر `reporterAccountId` المطابقة لمعرف حسابه فقط، والمهندس على التذاكر المسندة إليه فقط، والمدير على جميع التذاكر. لا تمنح أسماء الموظفين أو أرقامهم أو هوية منشئ البلاغ اليدوي صلاحية القراءة. تعيد التفاصيل `404` للسجل غير الموجود أو خارج نطاق المستخدم. تعيد عملية الإنشاء التذكرة لمنشئها؛ لا يسمح ذلك للمهندس بقراءة بلاغه اليدوي لاحقًا ما لم يُسند إليه.

يتطلب كل طلب إنشاء إدخال `reporterName` يدويًا، والقسم، ونوع العطل الرئيسي، و`title` و`description`. لا يستنتج الخادم الاسم من الحساب. يُرسل القسم إما كـ`departmentId` أو `department`، والنوع الرئيسي إما كـ`categoryId` أو `category`. يُرسل النوع الفرعي الاختياري كـ`subcategoryId` أو `subcategory`. لا تجمع المعرف والاسم لنفس الحقل؛ يحل الخادم الأسماء إلى سجلات نشطة، ويتحقق أن النوع الفرعي نشط ويتبع النوع الرئيسي المختار. إذا لم يُحدد نوع فرعي تحفظ القيمة الوصفية `عام` ومعرف فارغ. تحفظ أسماء القسم والأنواع وأسماء منشئ البلاغ والمهندس والمدير كلقطات تاريخية؛ لا تؤثر إعادة تسميتها أو تعطيلها لاحقًا في التذاكر القديمة.

مثال طلب موظف (ترسل الواجهة ملف ارتباط الجلسة و`Origin` المعتمد):

```json
{
  "reporterName": "اسم موظف خيالي مدخل يدويًا",
  "departmentId": "معرف قسم نشط",
  "categoryId": "معرف نوع عطل نشط",
  "title": "عطل تجريبي بالطابعة",
  "description": "تفاصيل خيالية للمشكلة",
  "createdFor": "self",
  "clientRequestId": "unique-submission-key"
}
```

للموظف، تكون `source` افتراضيًا `portal` و`createdFor` افتراضيًا `self` ويمكن تحديدها `other` للبلاغ بالنيابة. يبقى مالك الحالتين الحساب الذي أرسل الطلب، ولا يصبح الشخص المذكور في الاسم أو `employeeNumber` مالكًا. يرفض الخادم حقول `reporterAccountId`, `createdByAccountId`, `createdByName`, `createdByRole` بدل الوثوق بها. يمكن إضافة `employeeNumber` اختياري حتى 80 حرفًا؛ لا يستخدمه الخادم للتفويض.

للمهندس أو المدير، تكون `source` افتراضيًا `manual`، ويجوز تحديد `requesterType` كـ`employee` أو `top_management`. تتطلب الإدارة العليا `managementPosition` إضافة إلى الاسم والقسم المدخلين، ولا تقبل رقم موظف. يمكن إرسال اسم القسم `الإدارة العليا` إذا كان مسجلًا ونشطًا. تُحفظ هوية منشئ البلاغ من الجلسة ويكون `reporterAccountId` فارغًا؛ لا يُسند البلاغ إلى حساب موظف بناء على الاسم أو الرقم، ولا يقبل البلاغ اليدوي `createdFor`. لا يمكن للموظف إنشاء بلاغ يدوي أو للمهندس والمدير إنشاء بلاغ بوابة موظف.

تبدأ التذاكر `new` دون إسناد. يجوز للمدير فقط تقديم `assignedTechnicianId` عند إنشاء بلاغ يدوي؛ يجب أن يكون مهندسًا نشطًا، ويجوز أن يكون غير متاح مؤقتًا. عندها تحفظ التذكرة والإسناد وهوية المدير وسجلا `new` و`assigned` في معاملة واحدة وتصبح الحالة `assigned`. تتوفر بقية إجراءات دورة العمل أدناه، ولا توجد تقييمات أو أولوية أو صيانة يدوية منفصلة.

يدعم `GET /api/tickets` المعاملات `search`, `status`, `creationDate`, `sort`, `departmentId`, `categoryId`, `page`, `pageSize`. الحالة الافتراضية `all`، والترتيب `newest` أو `oldest`، والصفحة الأولى افتراضيًا وحجمها 50 بحد أقصى 100. التاريخ يوم صحيح بصيغة `YYYY-MM-DD` ويطبق على يوم الإنشاء بتوقيت UTC. يبحث الموظف في رقم التذكرة وعنوانها؛ ويشمل بحث المهندس اسم المبلّغ والقسم، ويضاف اسم المهندس لبحث المدير، وفق عقود الخدمة التجريبية. يستخدم ترتيب المهندس تاريخ الإسناد، ويستخدم الآخرون تاريخ الإنشاء، مع المعرف لفصل التعادل. يقبل المدير وحده `assignment=all|assigned|unassigned`. ترفض مرشحات معرف المالك أو المهندس أو الدور حتى لا تتجاوز نطاق الجلسة. تعيد القائمة `{ items, total, page, pageSize }`؛ لا تشمل عناصر القائمة السجل، بينما تعيده التفاصيل والإنشاء ضمن `{ item }`.

يمكن تقديم `clientRequestId` اختياري بطول 1–128 من الأحرف الإنجليزية والأرقام و`_` و`-`. يكون فريدًا داخل حساب المنشئ فقط؛ يعيد الطلب المطابق التذكرة نفسها بحالة HTTP `200`، ويعيد الإنشاء الجديد `201`، ويعيد استخدام المفتاح ببيانات مختلفة `409`. يحمي قيد فريد من التكرار المتزامن، ولا تتكرر أحداث السجل. تعمل إعادة الطلب المطابق بعد تعطيل البيانات المرجعية أيضًا. يُقارن الطلب بعد تطبيع المدخلات؛ تغيير طريقة تحديد المرجع من الاسم إلى المعرف يعد تغييرًا للطلب.

حد الاسم 160 حرفًا، والعنوان 200، والوصف 4000 مع دعم الأسطر الجديدة. حد جسم طلب التذكرة 32KB؛ تبقى بقية الواجهات على 8KB. كل الاستعلامات بمعاملات مربوطة، والبحث يعامل `%` و`_` كنص لا كبدائل SQL. تشمل اختبارات MySQL العزل بين الحسابات وتذاكر الآخرين والبلاغات اليدوية والتحقق من البيانات المرجعية واللقطات التاريخية والبحث والتصفية والإسناد الأولي ومنع التكرار المتزامن. تحذف الاختبارات فقط سجلاتها الخيالية.

## دورة العمل وسجل النشاط

تعيد إجراءات التذكرة `{ item }` وتتطلب جلسة نشطة و`Origin` مطابقًا. تتضمن التذكرة `version` يبدأ من صفر ويزيد مرة لكل إجراء ناجح يغيرها. يجب أن يرسل المدير `expectedVersion` الحالي عند الإسناد؛ تقبل بقية الإجراءات هذا الحقل اختياريًا للتحقق من أن المستخدم يعمل على النسخة التي قرأها. يعاد `409` عند اختلاف الإصدار أو تعارض الحالة؛ يجب إعادة تحميل التذكرة قبل المحاولة. الإسناد للمهندس نفسه دون تغيير لا يضيف حدثًا ولا يزيد الإصدار.

| الطريقة والمسار | الدور | جسم الطلب |
| --- | --- | --- |
| `POST /api/tickets/:id/assignment` | المدير | `technicianId`, `expectedVersion` |
| `POST /api/tickets/:id/claim` | المهندس المتاح | `{}` أو `expectedVersion` |
| `POST /api/tickets/:id/status` | المهندس المسند إليه | `status` وسبب التعليق أو وصف الحل حسب الحالة |
| `POST /api/tickets/:id/notes` | المهندس المسند إليه | `text`, `visibility` بقيمة `public` أو `internal` |
| `POST /api/tickets/:id/comments` | الموظف المالك | `text` |
| `POST /api/tickets/:id/confirm-resolution` | الموظف المالك | `{}` أو `expectedVersion` |
| `POST /api/tickets/:id/reopen` | الموظف المالك | `reason` اختياري، و`expectedVersion` اختياري |
| `GET /api/tickets/unassigned` | المهندس أو المدير | `page`, `pageSize` اختياريان |

تعرض قائمة غير المسندة ملخصات التذاكر `new` غير المسندة فقط: المعرف والعنوان والقسم والتصنيفات والحالة وتاريخ الإنشاء، دون الوصف أو بيانات المبلّغ أو الملاحظات. تعيد `{ items, total, page, pageSize }`. يجوز للمهندس غير المتاح قراءة الملخصات، لكنه لا يستطيع تولي تذكرة جديدة حتى يصبح متاحًا. يعرض `GET /api/tickets?scope=all` جميع البلاغات للمهندس، ويمكنه قراءة تفاصيلها دون تعديل بلاغات الزملاء أو البلاغات غير المسندة؛ تبقى إجراءات الحالة والملاحظات وسحب الأصل مقتصرة على المهندس المسند إليه. يظل الاستعلام دون `scope=all` مقصورًا على تذاكر المهندس نفسه لتغذية لوحة التحكم.

يمكن للمدير إسناد التذكرة أو إعادة إسنادها إلى مهندس نشط حتى لو كان غير متاح مؤقتًا. تتحول `new` إلى `assigned`؛ وتحافظ إعادة الإسناد على بقية الحالات بما فيها الحل والإغلاق. يسجل الخادم هوية المدير الحالية ولقطة اسمه في `assignedByManagerId/Name`. يسمح التولي الذاتي فقط للمهندس النشط والمتاح على تذكرة `new` غير مسندة، ويملأ `assignedByTechnicianId/Name` ويترك حقول المدير فارغة. تمسح إعادة الإسناد الإدارية حقول التولي الذاتي الحالية، مع إبقاء الأحداث السابقة بأسماء وهوية منفذيها.

تستخدم الإجراءات معاملة تقفل حسابات المنفذ والمهندس المطلوب بترتيب ثابت، ثم تقفل التذكرة بـ`FOR UPDATE` قبل التحقق والكتابة. تتزامن فحوص النشاط والتوفر مع تعديل الحساب، وتمنع حالة التذكرة والإصدار استيلاء مهندس ثانٍ أو الكتابة فوق إسناد متزامن. يعاد فحص هوية المنفذ ودوره داخل المعاملة. تفقد هوية المهندس السابق حق تعديل التذكرة عند إعادة الإسناد. عند التعارض لا تحفظ تغييرات جزئية أو أحداث مكررة.

الانتقالات المسموحة للمهندس المسند إليه:

| الحالة المطلوبة | الحالات السابقة المسموحة | البيانات الإضافية |
| --- | --- | --- |
| `in_progress` | `assigned`, `pending`, `reopened` | لا شيء |
| `pending` | `assigned`, `in_progress`, `reopened` | `pendingReason` غير فارغ حتى 2000 حرف |
| `resolved` | `assigned`, `in_progress`, `pending`, `reopened` | `solutionDescription` غير فارغ حتى 4000 حرف |

لا تمنع حالة عدم التوفر المؤقت العمل على التذاكر المسندة بالفعل. تمسح العودة للعمل أو الحل سبب التعليق الحالي، ويظل السبب السابق وتوقيته محفوظين في السجل. يقبل تأكيد الموظف فقط `resolved` وينقلها إلى `closed`. تقبل إعادة الفتح `resolved` أو `closed` وتنقلها إلى `reopened` مع سبب اختياري محفوظ. تبقى الإسنادات كما هي عند إعادة الفتح. يُمسح تأكيد الحل الحالي عند إعادة الفتح، وتبقى أوصاف الحلول السابقة وأوقاتها وتأكيداتها وكل أسباب إعادة الفتح محفوظة في الأحداث السابقة. التذكرة اليدوية التي لا تمتلك حساب موظف لا يمكن تأكيدها أو إعادة فتحها باسم موظف غير مرتبط؛ لا يوجد تجاوز إداري لهذا الشرط.

تقبل ملاحظات المهندس فقط الحالات `assigned`, `in_progress`, `pending`, `reopened`. يستطيع المدير قراءتها ولا يكتبها نيابة عن المهندس. تعليقات الموظف متاحة لمالك التذكرة في كل حالاتها ولا تغير الحالة. تُؤخذ هوية كاتب التعليق أو الملاحظة واسمه من الجلسة وقاعدة البيانات؛ تُرفض حقول انتحال الكاتب والحقول غير المعروفة. لا تتوفر واجهة تعديل أو حذف للملاحظات والتعليقات والأحداث.

السجل هو المصدر المحفوظ للملاحظات والتعليقات والحلول وإعادة الفتح. يخصص كل حدث رقم تسلسل داخل قفل التذكرة، مع نوعه وحالته وهوية الفاعل ولقطة اسمه ودوره ووقته والنص وبيانات الإسناد السابقة والجديدة عند اللزوم. تتضمن التفاصيل `history`, `publicTechnicianNotes`, `comments`، ولأدوار IT المسموح لها بالتفاصيل فقط `internalTechnicianNotes`. تُستبعد الأحداث الداخلية في استعلام SQL للموظف، ولا تُرسل نصوصها أو بياناتها أو مصفوفة ملاحظاتها في تفاصيله أو ردود التعليق والتأكيد وإعادة الفتح أو إعادة طلب الإنشاء. يتحقق تكرار الإنشاء أيضًا من نطاق الدور الحالي؛ لا يمكن لمنشئ بلاغ يدوي غير مسند إليه استخدام مفتاح الإنشاء القديم لقراءة ملاحظات أضيفت بعد إسناده لشخص آخر.

تتحقق الاختبارات الحية من مصفوفة الصلاحيات والانتقالات وأسباب التعليق والحلول الإلزامية وسلامة السجل بعد دورات حل وإعادة فتح متكررة، ومن خصوصية الملاحظات الداخلية، ومن سباقات التولي والإسناد بين المديرين والإسناد مع كتابة المهندس وتعديل التوفر والملاحظات المتزامنة والتأكيد المتكرر. لا تتضمن هذه المرحلة أولوية أو تقييم خدمة أو واجهة أمامية أو إشعارات آنية.

## الأصول التقنية والكميات والتصدير

الترحيل `005_assets.sql` يضيف `assets`, `asset_history`, `asset_withdrawals` ويربط التذكرة بالأصل المسحوب عبر `related_asset_id` ويضيف نوع حدث داخلي للسحب. لا يغير ملفات الترحيلات السابقة. يُترك الترحيل محفوظًا ضمن سجل الترحيلات؛ وقد طُبّق محليًا خلال المراجعة الأخيرة، ولا تحتاج تغييرات الكود أو الاختبارات المعزولة إلى إدخال كلمة مرور الإدارة. يمنح سكربت الترحيل حساب التطوير القراءة والإنشاء والتعديل على الأصول والقراءة والإضافة فقط على التاريخ والسحوبات؛ يملك حساب الاختبار صلاحيات تنظيف سجلاته.

| الطريقة والمسار | الصلاحيات والوظيفة |
| --- | --- |
| `GET /api/assets` | المهندس والمدير: قائمة المخزون والبحث والتصفية |
| `POST /api/assets` | المهندس والمدير: إنشاء سجل كمية |
| `GET /api/assets/:assetId` | المهندس والمدير: التفاصيل وسجل التغييرات، حتى بعد الأرشفة |
| `PATCH /api/assets/:assetId` | المهندس والمدير: تعديل مع `expectedVersion` |
| `POST /api/assets/:assetId/archive` | المدير فقط، مع `{ "expectedVersion": 0 }` حسب الإصدار الحالي |
| `GET /api/assets/export.xlsx` | المهندس والمدير: ملف Excel عربي RTL للمخزون النشط المطابق للمرشحات |
| `POST /api/assets/:assetId/withdraw` | المهندس المسند إليه بلاغ نشط: `{ "ticketId": "UUID" }` و`expectedVersion` اختياري للأصل |

الموظفون لا يملكون الوصول لأي واجهة مخزون أو تصدير أو سحب. تُستمد هوية المنفذ واسمه ودوره من الجلسة وحساب قاعدة البيانات؛ لا تقبل الواجهات ادعاءات الكاتب أو المهندس أو معلومات السحب في التعديل العام.

حقول الإنشاء: `assetId`, `name`, `quantity`, `manufacturer`, `model`, `location`, `operationalStatus`, `conditionDescription`، مع `serialNumber`, `purchaseDate`, `maintenanceNotes`, `lastMaintenanceDate` اختياريًا. المعرف ثابت، يحول إلى أحرف إنجليزية كبيرة، وطوله 3–40 ويقبل الأرقام والحروف و`.` و`_` و`-` فقط. الكمية عدد صحيح بين 1 و1000000؛ تمنع قيود قاعدة البيانات الكمية الصفرية والسالبة. التواريخ أيام صحيحة بصيغة `YYYY-MM-DD` أو قيمة فارغة. تُرفض حقول تصنيف الأصل والتقييم بالنجوم في المدخلات والمرشحات ولا تظهر في البيانات أو التصدير.

تكون `holdingType` افتراضيًا `department` وتتطلب اختيار قسم نشط عبر `departmentId` أو اسم `department`، ويُحفظ اسمه كلقطة. يمكن اختيار `holdingType: "it_storage"` للمخزون الاحتياطي والأكسسوارات؛ عندها لا يرسل قسم وتظهر القيمة الوصفية `مخزن تكنولوجيا المعلومات` مع الموقع الفعلي المطلوب. عند تغيير نوع الحيازة من المخزن إلى قسم يجب اختيار القسم صراحة. يحفظ سجل الأصل عمليات الإنشاء والتعديل والأرشفة والسحب بهوية المنفذ ووقته والقيم السابقة واللاحقة والحقول التي تغيرت.

الحالات التشغيلية: `working`, `needs_maintenance`, `out_of_service`, `under_repair`, `retired`, `withdrawn`. حالة `withdrawn` محجوزة لعملية السحب: لا يمكن إنشاء أصل بهذه الحالة أو تحويل أصل عادي إليها بالتعديل العام. تبقى كمية الوحدة المسحوبة واحدة ولا يمكن إعادتها إلى حالة أخرى من واجهة التعديل. تبقى بيانات السحب وعلاقتها بالتذكرة ثابتة؛ ويمكن تعديل البيانات الوصفية المسموح بها مع حفظ التاريخ. لا توجد واجهة حذف؛ الأرشفة تحفظ السجل والعلاقات وتخفيه من القائمة الافتراضية وتمنع تعديله أو سحبه.

مرشحات القائمة: `search`, `departmentId` أو `department`, `holdingType`, `operationalStatus`, `includeArchived=true|false`, `page`, `pageSize`. يبحث النص في رقم الأصل والاسم والموديل والرقم المسلسل، مع دعم العربية ومعاملة بدائل SQL كنص. الترتيب ثابت برقم الأصل؛ حجم الصفحة الافتراضي 50 وبحد أقصى 100. تعيد القائمة `{ items, total, page, pageSize }`. تعيد التفاصيل والإنشاء والتعديل والأرشفة `{ item }`، ويتضمن السجل `version` و`history`.

التصدير يستخدم المرشحات نفسها لجميع النتائج المطابقة دون ترقيم صفحات، ويستبعد المؤرشف دائمًا. تُرفض معاملات الصفحات وطلب تضمين المؤرشف. الحد 10000 سجل؛ ترجع النتائج الأكبر `413` لطلب تضييق المرشحات بدل اقتطاع صامت. ملف `.xlsx` حقيقي بمكونات Open XML مضغوطة باستخدام `fflate`، ورؤوس عربية واتجاه ورقة ومحاذاة RTL وصف رؤوس ثابت. الكمية خلية رقمية؛ النصوص كلها خلايا نصية صريحة بما فيها القيم التي تبدأ بـ`=`, `+`, `-`, `@`، ولا تنشأ صيغ Excel من المدخلات. يتضمن التصدير معلومات الكمية والحالة والصيانة واسم المهندس والتذكرة المرتبطة عند السحب، دون الحقول الملغاة.

يشترط السحب أن يكون المنفذ مهندسًا نشطًا، والتذكرة مسندة إليه بحالة `assigned`, `in_progress`, `pending` أو `reopened`، والأصل غير مؤرشف وحالته `working`. لا تمنع حالة عدم التوفر المؤقت العمل على تذكرة مسندة بالفعل. لا يستطيع المدير السحب نيابة عن المهندس، ولا يقبل الخادم كمية للسحب أو هوية مهندس من العميل.

تتحقق المعاملة من حساب المنفذ ثم تقفل التذكرة ثم الأصل، بنفس ترتيب قفل دورة العمل. عند كمية أكبر من واحدة، تنقص كمية المصدر بواحد فقط ويُنشأ سجل مستقل بمعرف عشوائي ثابت `WD-...` وكمية واحدة وحالة `withdrawn`؛ لا يُنسخ الرقم المسلسل الخاص بالدفعة إلى الوحدة. عند كمية واحدة، تبقى هوية الأصل نفسها وتتحول حالته إلى `withdrawn` دون إنشاء سجل صفري. تُحفظ هوية المهندس ولقطة اسمه والتذكرة والمصدر ووقت السحب في علاقة منفصلة. يُضاف حدث إلى سجل المصدر وسجل الوحدة الجديدة عند التقسيم وحدث داخلي إلى تاريخ التذكرة، ويزيد إصدار التذكرة. لا يصل حدث السحب الداخلي إلى الموظف.

المفتاح الأساسي لعلاقة السحب هو معرف التذكرة، مما يمنع أكثر من وحدة للتذكرة نفسها حتى من مصادر مختلفة، ومعرف الوحدة المسحوبة فريد. تمنع أقفال المصدر والقيود السحب الزائد بين تذاكر متزامنة، ويُلغى أي تعارض أو فشل بالكامل دون تغييرات جزئية. تعيد العملية `{ asset, remainingSource, ticket }`؛ تكون `remainingSource` فارغة عند التحويل في المكان. لا تُحدّث مراجع التذاكر أو أسماء تاريخية عند تعديل بيانات الأصل.

أوامر الاختبارات:

```powershell
npm run lint
npm test
npm run test:integration:core
npm run test:integration:assets
```

يشغّل `test:integration:core` اختبارات المصادقة والإدارة والتذاكر السابقة دون الحاجة للترحيل الجديد. تتطلب `test:integration:assets` تطبيق `005` وصلاحياته مسبقًا؛ تفشل برسالة واضحة إذا كان الترحيل مؤجلًا ولا تُعلن نجاحًا بتجاوز الاختبارات. يشغّل `test:integration` المجموعتين. تغطي اختبارات الأصول المخزون والأرشفة وخصوصية الأدوار والتصدير والتقسيم والسحب في المكان ومنع السحب المكرر وسباقات المخزون وإعادة الإسناد. لا تُنشئ الاختبارات قواعد بيانات ولا تطبق ترحيلات، وتستخدم حسابات خيالية وتنظف سجلات تشغيلها فقط.

## الحدود الحالية والخطوات التالية

- اختبارات `npm test` معزولة، بينما تتحقق اختبارات `npm run test:integration` من المصادقة باستخدام قاعدة بيانات حية. يتحقق الإعداد المحلي بصورة منفصلة من الترحيل وإعادة تشغيله. جرى إعداد MySQL 8.0.46 محليًا على المنفذ `3307` لقواعد التطوير والاختبار.
- تحديد محاولات الدخول حاليًا داخل ذاكرة عملية واحدة؛ قبل تشغيل عدة نسخ استخدم مخزنًا مشتركًا وحدودًا مناسبة للحساب وعنوان IP.
- طبقة `localPasswordProvider` قابلة للاستبدال لاحقًا بمزوّد هوية خارجي. لا تُرسل كلمات مرور Windows Domain إلى هذا المزوّد المحلي.
- نفّذ تفويض الأدوار وملكية التذاكر على الخادم قبل نقل أي وحدة أعمال. لا تعتمد على حراسة المسارات في React.
- بيانات `localStorage` التجريبية وحسابات العرض في الواجهة لا تُرحّل تلقائيًا إلى MySQL. خدمات الواجهة متصلة الآن بـ API؛ لا تُستخدم السجلات التجريبية في جلسة API.
- قبل النشر، أضف إعدادات TLS، وإدارة الأسرار، ونسخًا احتياطية، ومراقبة، وترحيلات مُختبرة ضد نسخة MySQL المستهدفة.

### IT Assets authorization update

Engineers (`technician`) and Managers (`manager`) share full server-authorized access to all `/api/assets`, `/api/asset-management` and `/api/asset-management/simple` operations. Employees remain denied. See [the authorization policy](docs/asset-permissions.md). No migration or database administrator login is needed for this authorization change.

### Simple asset quantities

The simple asset API supports one nonserialized equipment record with `quantity` (default 1). Serialized types, including the configured PC cases, keep one device and serial per record. Migration 014 adds quantity safely; apply it with `powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\migrate-local-db.ps1` and enter the administrator password only in its hidden terminal prompt. Existing records default to quantity 1. See [quantity and frontend integration](docs/simple-assets.md#quantity-and-serial-policy-2026-11-12).
